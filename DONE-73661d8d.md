## Mechanism (a) — Task↔Card link (verified on origin/main 8c97de2c)

- Field: `Task.linkedCardId` (`backend/src/types.ts:336`) — "Another Card this Task is carried out
  by (a course's "Workshop 2" Task links that workshop's Card)". The linked Card keeps a back
  reference `Card.linkedFrom` (`backend/src/types.ts:411-415`, `TaskCardBackReference`
  `backend/src/types.ts:482-486`), written with the link and re-checked by readers.
- Authored template syntax: `link_card: { template_type, slot }` on a task — mapped losslessly in
  `backend/src/templates/yamlTemplates.ts` (`templateFromYaml` 199-202, `templateToYaml` 148-151)
  and validated at 364-373 (template_type slug required; slot 1-80 chars; `{n}` allowed in slot for
  repeat instances). Runtime type `TaskLinkCard` (`backend/src/types.ts:505-514`) carried on
  `TaskDefinition.linkCard` (`backend/src/types.ts:556-557`).
- Write path: `setTaskLinkedCard` (`backend/src/db/taskCardLinks.ts:75-86`, keeps
  `Card.linkedFrom` in sync); API action `POST /api/tasks/:id/actions/link-card`
  (`backend/src/routes/tasks.ts:901`); CLI `dataops tasks link-card <task-id> <card-id>` /
  `--unlink` (`cli/src/commands/tasks.mjs:47-48`, implementation 1075-1090).
- Automatic slot Cards: a Task whose definition has `link_card` with a `slot` gets its own undated
  event Card created and linked — `ensureEventSlotCards` (`backend/src/cards/eventSlots.ts:40-89`),
  exposed as `GET/POST /api/cards/:id/event-slots` (`backend/src/routes/cards.ts:392-393`, handler
  219-229) and run automatically after Card creation (`backend/src/routes/cards.ts:535`); failure
  degrades to `dataops cards event-slots <card-id> --apply` (`backend/src/routes/cards.ts:215`).
  Slot naming substitutes `{n}` with the repeat instance number
  (`backend/src/cards/taskLinkCard.ts:11-13`). CLI: `dataops cards event-slots <card-id> [--apply]`
  (`cli/src/commands/cards.mjs:34`, 438-440).
- Done-guard: a Task with a `link_card` definition cannot be marked done without
  `linkedCardId` (`backend/src/routes/taskValidation.ts:588-595`), and
  `validation.requiresLinkedEventCards: true` (used by the course template's `prepare-events`)
  blocks completion until every open slot Task on the Card links its event Card
  (`backend/src/routes/taskValidation.ts:580-606`).

## Mechanism (b) — count-driven repeatable tasks (verified on origin/main 8c97de2c)

- Authored template syntax: template-level `count_fields` (`id`, `label`, `default`, `min`, `max`;
  `0 <= min <= default <= max <= 50`) and per-task `repeat: { count_field }` — mapped in
  `backend/src/templates/yamlTemplates.ts` (`count_fields` 184-186, `repeat` 198; back-references
  130-131 and 147) and validated at 294-316 (`count_fields`) and 357-362 (`repeat` must name a
  declared count field). Task ids must not contain `#`, which numbers repeated instances
  (`yamlTemplates.ts:340`).
- Runtime types: `CountField` (`backend/src/types.ts:492-498`), `TaskRepeat`
  (`backend/src/types.ts:500-503`), `TaskDefinition.repeat` (`backend/src/types.ts:550-555`),
  `Template.countFields` (`backend/src/types.ts:690-691`), `Card.counts`
  (`backend/src/types.ts:409-410`).
- Expansion: `backend/src/templates/repeatedTasks.ts` — `MAX_COUNT = 50` (20), instance refs
  `workshop#1..#N` (25-33), `{n}` description substitution (36-40), `cardCountValues` (43-48),
  `countValuesError` (58-68), `expandTaskDefinitions` (100-140; consecutive repeated definitions
  with the same count field interleave as one group and instance n of a member depends on instance
  n of the members it names). Wired into Card creation via `selectedTaskDefinitions`
  (`backend/src/templates/cardTemplateProjection.ts:56-66`) and stored on the Card by
  `templateLinkage` (`cardTemplateProjection.ts:97-111`); counts validated at Card creation
  (`backend/src/cards/createCard.ts:322-324,341`).
- Count changes: `dataops cards update <card-id> --count FIELD=N --apply` is a reviewed Template
  update; raising adds numbered instances, lowering keeps instances that are done or link a Card
  (`retainedRepeatIndexes`, `backend/src/templates/repeatedTasks.ts:75-91`) so the group's
  dependencies stay intact; applied in `backend/src/templates/cardTemplateUpdates.ts:306-351`.
- CLI: `dataops cards create --count FIELD=N,...` (`cli/src/commands/cards.mjs:26`),
  `dataops cards update --count` (29-30), `dataops cards template-update --count` (51); help text
  documents the model (65-67).

## Remaining gaps (not asked, noted for the handoff)

- Counts are operator-entered integers on the Card (`cards create --count`, `cards update --count`),
  not derived from external data: "one social post per campaign-calendar row" is not auto-counted
  from the linked Campaign calendar Card — the owner sets the number when creating/updating the
  Card. Deriving counts from a linked Card's contents would be new backend behavior, out of scope
  here.
- `maven-cohort.yaml`'s `lightning-lesson` uses `link_card` without `slot`, so no slot Card is
  auto-created for it (`eventSlots.ts:55-56` skips slot-less definitions); the definition still
  enforces a manual `tasks link-card` at completion (`taskValidation.ts:588-595`). This looks
  intentional (Maven lessons are scheduled in Maven), just worth knowing.
